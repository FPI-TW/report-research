# ext4 vs 9p — read-only benchmark

- **舊**：`/mnt/c/Users/User/Desktop/Project/report-mark` — **9p**（drvfs，`cache=0x5`，`msize=65536`）
- **新**：`/home/kashionz/projects/report-mark` — **ext4**（`/dev/sde`）
- 方法：Python `time.perf_counter()`，每項 **6 輪、丟棄第 1 輪 warm-up、取 5 輪中位數**
- 執行位置：`/tmp`，腳本不放在任一 repo 內
- 原始資料：`raw-results.json`、`raw-results-2.json`、`summary.json`

## 唯讀性證明

所有 git 指令均以 `GIT_OPTIONAL_LOCKS=0` 執行，並在全部 benchmark 前後量測 `.git/index` mtime：

```
old repo .git/index  before=1787037767.8477316  after=1787037767.8477316  UNCHANGED
new repo .git/index  before=1787033227.1611257  after=1787033227.1611257  UNCHANGED
```

兩個 repo 的 index 皆未被改寫，Python 端只用 `os.walk` / `os.stat` / `open(..., "rb").read()`。
`git status` **刻意未納入** benchmark——它會刷新 index 的 stat cache，不符合「嚴格唯讀」。

## Conclusions

**1. 哪些操作改善最大？**
純 metadata 操作。`stat` 從 754.5 µs 降到 1.12 µs —— 9p 的每次 `stat` 幾乎都是一次
往返 Windows 的 RPC（`cache=0x5` 不積極快取 metadata、`msize=65536` 又限制了批次大小），
ext4 則直接命中 page cache。

**2. Git 類改善多少？** **14x–620x，幾何平均 44.1x**。差異來自各指令的 metadata 密度：
`git grep`（掃內容，14.1x）最小，`git diff --stat`（要 stat 每一個 tracked 檔，620.5x）最大。
`git rev-parse` 這種「只開幾個 `.git` 小檔」的操作也有 26.5x，說明**連最輕的 git 操作
在 9p 上都要付出可觀的固定成本**。

**3. Source tree traversal 改善多少？** **T1b = 776.1x**（975.94 ms → 1.26 ms）。
對只有 736 個檔案的原始碼樹，9p 需要將近 1 秒；ext4 是 1.26 毫秒。

**4. 9p penalty 是否主要出現在 metadata syscall？**
**是，證據明確。** T6（純 `stat`，671.6x）與 T2（`stat`+讀 4 KiB，421.1x）相比，
**加上實際讀取後 speedup 反而下降** —— 若瓶頸在資料頻寬，加讀取應該讓差距擴大而非縮小。
T4（`git grep`，內容掃描）只有 14.1x，是全部項目中最低的，同樣指向同一結論：
**9p 的代價集中在每次 metadata 往返的固定延遲，而非傳輸吞吐。**

**5. 這些結果是否足以支持「repo / venv / node_modules 放 ext4」？**
**是。** 依賴樹是本 repo 檔案數最多的部分（`.venv` 5.5 GB、`frontend/node_modules` 393 MB，
合計數萬個小檔），而它們的存取模式幾乎純粹是 metadata（import 解析、套件安裝的
`stat`/`rename`/`mkdir`）。以 754.5 µs/stat 計，一次 Python 直譯器啟動的數千次 `stat`
就是秒級成本。這也與 2026-08-18 事故一致：`uv` 的 `.tmp*` → 正式路徑 rename 在 9p 上
以 `os error 2` 失敗（見 postmortem），**那不只是慢，是正確性問題**。

**6. 哪些結果不能用來推論 production latency？**
**全部都不能直接推論。** 本組 benchmark 量的是**檔案系統的 metadata 延遲**，而生產的
使用者可見延遲由完全不同的東西主導：

- `/api/ask` 的首 token（實測 48.2 秒）幾乎全部是 **Claude CLI 子行程 ＋ LLM 推論**
- 檢索延遲由 **BGE-M3 嵌入（CPU）＋ pgvector HNSW（Docker volume，不在 9p 上）** 決定
- DB 完全不受影響：`report-mark-pgdata` 是 Docker volume
- 模型權重在 `~/.cache/huggingface`（**遷移前就已在 ext4**）

**可以合理推論的是**：冷啟動（`uv run` 解析環境、Python import 數千個模組）、
git 操作、開發期的測試與建置、以及**批次管線中大量 `stat` 的部分**。
**不可以推論的是**：HTTP 回應時間、LLM 延遲、向量檢索延遲。
